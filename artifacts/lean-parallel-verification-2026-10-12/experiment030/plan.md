# Experiment030: complete native verification response cost

## Research question
RQ3: How does prepared-state branching change end-to-end latency, throughput and
memory at equal resources compared with established warm-session reuse?
Tested supporting uncertainty: after competent native preparation reuse, does
avoidable response extraction materially limit complete native verification?
This supplies a stronger CPU/native service path, not a new central contribution.

## Admission and competing explanation
Role: supporting a decisive complete service/heterogeneous comparison.
Source evidence: retained and current official REPL stringify an entire Syntax to
classify fixed sorry nodes, then traverse info trees twice. Pinned formatter emits
a node header from kind.replacePrefix Lean.Parser; non-node formats cannot match
the parenthesized fixed target. A cheap necessary header test can reject most nodes
before the original exact predicate. Original positive cases still execute the same
reference predicate; no sorry/diagnostic filtering is introduced.
The potential story is response preparation dominating residual warm checking,
making a kernel-only accelerator target the wrong cost. It is not proven by code
inspection and not novelty for AST matching.
Positive full-workflow evidence strengthens the CPU competitor and informs broader
system work; negligible/negative results close this optimization. Fairness/artifact
differences invalidate superiority, not an excuse to suppress diagnostics.
Alternative: more shared-process/GPU microvariants are already negative and low
value. Actual complete response-cost discrimination is a new causal uncertainty.
