# E1067: native integer arithmetic as a strong competing CPU control
## RQ and admission
RQ4: After preparation reuse, when does heterogeneous execution improve complete verification over the strongest measured CPU path?
Role: decisive baseline-pressure control. Current native-ranked heavy-tail data show almost no direct numerical-search time in the hardest1%, while several sources enumerate many Nat/Int subgoals. The official Lean4.27 omega tactic is a plausible stronger native algorithm for these goals. No existing matched omega result was found in the current paper/evaluation/implementation/closest-work map.
Hypothesis: a guarded use of stock omega before the existing native frontend and two-sided numerical backend materially reduces this residual work, changing the strongest-CPU comparator. This is existing proof-search technology, not new systems contribution or GPU performance.
Positive result weakens any claim that the current direct frontend or GPU reaches a new CPU frontier; unchanged/losing result bounds this specific competitor. Verdict mismatch invalidates transparent speed comparison. Strongest alternative next experiment is the ongoing complete29750 component study, already running; this control adds an independent algorithmic falsifier without duplicating or mutating it. Another small LP kernel has lower decision value given current parsed-solver and tail costs.

Candidate: existing direct AST+same two-sided backend. Component control: same native frontend/backend with omega disabled. The original Fast/hybrid remains a historical control, not another full weak row.

## Real preflight and full acquisition
Input selection is fixed before this control runs: earliest original-order source with an observed unsupported-carrier fallback and an actual bare unparameterized arithmetic tactic, earliest Real/Rat source, and all eight original rejected source controls. Duplicates removed in original order; no new performance-based selection.
Preflight three conditions in fixed order: native-dual-off, native-dual-omega, direct-dual-off. Original source order/bytes. Engagement log must show a real guarded omega attempt and native proof acceptance. All original outcomes/non-message fields must match.
If preflight shows meaningful supported work and better native elapsed while matching outputs, qualify the direct frontend with the same omega control, then run the same full1000 original cohort at matched resources in three conditions: native-dual-omega, direct-dual-omega, and existing direct-dual-off as a component control. This gives both frontend families the same stock discrete solver. The known slower native-dual-off is not repeated as another full row. If outcome mismatch or no worthwhile benefit, retain the control and do not open a full tuning matrix. This is a predeclared algorithmic control, not E038 runtime branching.
If the native competitor wins, record that the current speedup is not beyond the strongest measured CPU path; do not close overall GPU without the user's applicable Amdahl condition. If direct remains faster, scope the result to these methods. No global optimality or confidence claim from one preflight/pair.
