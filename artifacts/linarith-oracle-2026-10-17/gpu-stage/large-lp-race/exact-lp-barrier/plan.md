# FP-failed LP head: independent original-feasibility GPU solve

Root is sole executor and reviewer. This is a selected diagnostic admission
within the existing arithmetic/GPU RQ, not final 1,000-source evidence or
a new solver-selection contribution. The four RQs and OSDI target stay open.

The complete queue profile does not establish a below-1.5x ceiling:
numeric product/LP intervals occupy 411.683 of 545.050 oracle seconds.
The optimistic fixed-timeline deletion model is 5.18274x against its own
691.205-second native reference; overlap and concurrent non-GPU work prevent
treating it as achievable acceleration or a universal scheduling theorem.

Cheap FP fails on 1,888 oracle calls with 518.393 CPU seconds of exact LP work.
At least two candidates overlap in exact search for 221.404 seconds.
Median exact LP shape is 82 rows/230 columns. The previous whole-task-tail
qualification instead overselected expensive Nat proof construction. Freeze
the ten sources with largest native exact-LP CPU in this complete profile,
then retain original input order: 37,62,86,208,283,310,435,456,537,897.
This inspected subset is only a mechanism preflight. Do not relabel it fresh
headline evidence; the original 1,000 sources remain the final cohort.

Hypothesis: expensive FP-failed LPs can benefit from an accurate GPU basis
solver when independent cancellation and the original feasibility model
remove work introduced by the joint phase-I artificial-slack model.
Reuse the existing qualified FP-first provider. Keep row11, max8 candidates,
eight upstream contiguous sequential queues, native heartbeats, 48GiB,
zero cores, and CPU eligibility8-11 for all compared clients and numerical
server workers. No new array-wide deadline, tolerance or iteration grid.

Compare fresh native, CPU-only oracle, CPU HiGHS support racing exact CPU,
and GPU Barrier+crossover support racing the same exact CPU. The latter
is GPU factorization with CPU support repair and unchanged Lean proof checking.
The default historical PDLP joint phase-I path remains reproducible.
Independent jobs use original A*x=b,x>=0,c=0; no-certificate LPs may be
infeasible without poisoning a different job. First exact checked certificate
wins; CPU exact no-certificate may terminate the attempt. Cancel/reap losing
CPU workers and retire every cuOpt job. Same CPU eligibility does not imply
no contention overhead: measure it rather than promise worst-case parity.

Actual simultaneous LP RPC jobs are parallel admission, not a fused model
or proof of concurrent GPU kernels. Keep existing full-cohort fused-job
evidence separate. Report submitted models, cross-source overlap, winners,
cancellations, retirements, failures, complete-cold lifecycle, and primary
whole verification clocks. A fresh HiGHS win is a stronger CPU baseline,
not GPU acceleration. Any Concurrent-method CPU win must not be called GPU;
this candidate explicitly selects Barrier.

Implementation uses upstream pinned cuOpt26.10 gRPC API, eight existing
finite workers and the same approved temporary Job name on RTX5090 only.

https://docs.nvidia.com/cuopt/user-guide/latest/convex-features.html

Barrier uses GPU sparse factorization and crossover for a basic solution;
canceling a running server job kills/respawns its worker. Charge that cost.

Decision: correct complete-cost gain over the strongest fresh CPU competitor
admits one fresh full1,000-source matched comparison. A slower/invalid result
rejects this integration, not all GPU directions. Only an applicable below1.5x
bound or completed effective GPU evaluation can resolve the user's overall
criterion; CPU-only earlier ratios cannot close the route.

Self-review: selected LP-heavy qualification can exaggerate opportunity and
has no repeatability claim. Inspecting a few success branches cannot substitute
for all-call profiling; full cohort checks must retain failures and warnings.
The strongest alternate action is optimizing Nat/Int coverage, already tried
and slower. This experiment instead targets observed dominant numerical work.
