## Material defects and minimum repair

1. **Asymmetric supervisor delay contaminates preparation-cost attribution.** Fresh `capture()` repeatedly calls `proc.poll()` then waits up to 0.05 seconds before checking again; `process_end` is recorded only after that observation and owned-group teardown. Warm `Session.call()` uses stdout readiness and detects the response without an equivalent fixed wait. Serial fresh verification therefore accumulates observer delay once per input; its invocation distributions are quantized and complete corpus clocks include that extra delay. Across 13,760 inputs, a nominal 50 ms per-input upper contribution would be 688 seconds before host scheduling delays. This is a source-derived bound on instrumentation, not a measured bias. Complete corpus clocks cannot remove it: the supervisor also delays admission of the next input. A resulting cold/warm difference cannot all be attributed to native preparation. Use prompt process-exit observation with signal-responsive ownership, or explicitly measure and bound the asymmetric observation component tightly enough that it cannot determine the claimed effect/interpretation. Retain true fresh process launch/exit/teardown versus warm response and lifecycle boundaries; different lifecycle costs themselves belong in the comparison. Do not subtract an assumed 25 ms average.

No analysis entrypoint was found in the inspected bench inventory for these raw layouts. This is acknowledged incompleteness, not a false result claim; nevertheless full executable PLAN REVIEW cannot approve the end-to-end preflight until that ordinary analysis command exists. Freeze explicit clock boundaries, failed/timeout denominator policy, setup/teardown accounting, and interpretation of excluded numeric env/proofState handles. Include raw setup messages in qualification: the native Frontend returns only messages newly added after its restored state, so a header warning can disappear from the candidate response even though it remains in setup artifacts. Warm currently accepts setup with warnings/info. Do not silently drop such feedback; require an explicit comparison/fallback policy consistent with the existing promise.
