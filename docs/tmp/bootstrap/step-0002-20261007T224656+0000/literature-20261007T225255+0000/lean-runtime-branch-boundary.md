## Findings

**`LEAN_NUM_THREADS=1` does not disable the task manager or guarantee absence of background threads.** In `src/runtime/object.cpp:861–880`, the environment string is parsed by `atoi` and passed to `lean_init_task_manager_using`. Any positive worker count allocates a task manager in a multithread-enabled build. Constructor `task_manager:764` is lazy: it sets the maximum standard-worker count and does not immediately spawn one. Thus it is also incorrect to say that setting one always creates a live worker before a pure import response. On first queued task, `enqueue_core:610–623` can spawn a standard worker; `spawn_worker:645–669` runs a persistent loop that waits when its queue empties and exits only on shutdown. A finished task or empty queue therefore does not imply the worker has exited. Dedicated workers for priorities greater than `LEAN_MAX_PRIO` use `spawn_dedicated_worker:672–680` independently of the standard-worker cap. The numeric value one limits standard workers, not total execution threads including the caller and dedicated workers.

**There is a stock synchronous path, using zero workers before tasks/import, but it is not a documented fork-safety contract.** Public declarations `lean_init_task_manager_using`, `lean_init_task_manager`, `lean_finalize_task_manager` are in `src/include/lean/lean.h:1085–1087`. `lean_init_task_manager_using(0)` leaves `g_task_manager == nullptr`; so does normal initialization with `LEAN_NUM_THREADS=0`. `lean_task_spawn_core:943–951` executes the closure directly and returns `lean_task_pure` when no manager exists. `lean_task_map_core:965–974` and `lean_task_bind_core:1008–1017` likewise have synchronous no-manager branches. `lean_io_as_task` in `src/runtime/io.cpp:1035–1041` delegates to this spawn path. This is implemented stock behavior, with no solver/runtime patch required for these primitives; zero is not inferred from the colloquial meaning of a single thread.

**Native initialization is separate from starting the task manager.** `src/initialize/init.cpp:27–39` performs stack/runtime/Lean/module initialization but does not start the task manager. `src/util/init_module.cpp` calls runtime module initialization, whose body in `src/runtime/init_module.cpp` initializes allocator, IO, thread infrastructure, mutex and process infrastructure, not the task manager. Generated entrypoints in `src/Lean/Compiler/IR/EmitC.lean:164–178` initialize Lean, run the executable module initializer, mark end of initialization and only then call `lean_init_task_manager()` before invoking Lean main. They finalize the manager after main. This gives two narrow possibilities: use the original generated executable with `LEAN_NUM_THREADS=0` from launch, or a native host following the stock initialization sequence with `lean_init_task_manager_using(0)` before the import action. The latter is an embedding adapter and must be compared with the original interface; it cannot be called an unchanged executable. Reinitializing runtime after fork is not established by these functions.

**A response environment ID is not a synchronization primitive.** The exact retained REPL fork at `3334a97b268ecc67beb36a75787f7e831208a724` is xinhjBrant/repl, not silently substituted community HEAD. Its `REPL/Frontend.lean` calls `enableInitializersExecution`, parses a header when no old command state is given, calls stock `processHeader`, then `IO.processCommands`. The latter is the old sequential frontend loop; it is not the incremental language task pipeline. `Frontend.runCommandElabM` sets `snap? := none` and `cancelTk? := none`. The inspected `Command.elabCommand` promise allocation for incremental macro snapshots is guarded by `snap?`, so that particular route is absent for this caller. This does not exclude arbitrary task-producing elaborators/initializers.

REPL `runCommand` returns after processing inputs, messages, sorries and optional extraction, records a `CommandSnapshot`, and `repl` emits JSON plus a blank line before looping. It calls no global task-manager drain, shutdown, lock audit or fork hook at that response. The selected header-only request may have finished all of its direct work, but the response does not assert that no runtime work or live worker remains. Old REPL command state supports immutable logical backtracking independently of process branching.

## Import path and limits of the source argument

`src/Lean/Elab/Import.lean:25–34` calls `importModules` from `processHeader`. `Environment.importModules:870–877` runs `withImporting`, recursive `importModulesCore` and `finalizeImport`. The recursive file-loading loop is sequential at this level; `readModuleData` maps to `lean_read_module_data`, whose inspected implementation in `src/library/module.cpp:129ff` does ordinary stream/mapping/compacted-region work, without task spawning in that function. `finalizeImport` builds constant maps and extension state, calls `setImportedEntries` and `finalizePersistentExtensions`, and may mark the environment persistent.

The important escape is `finalizePersistentExtensions:721ff`, which invokes each extension's `addImportedFn` in `ImportM`/IO and may register additional extensions/attributes. This node does not exhaustively certify Mathlib or every user extension's callbacks, interpreted initializers, native dynamic libraries or FFI behavior. Initializers may execute arbitrary effects; absence of an `asTask` token in the outer import loop is insufficient.

`src/Lean/ImportingFlag.lean` explicitly states that executing initialization code is not safe with multiple threads, that global import references have no semaphore, and that callers of `importModules` must ensure only one execution thread accesses those globals. This is a single-accessor requirement, not an assertion that no idle worker exists. It also warns that loaded native code must match imported versions, two versions must not be loaded, native code must not be loaded after importing its module, and compacted regions must not be freed while cached initializer results may refer to them. `withImporting` restores importing and initializer-enable flags in `finally`; restoring flags does not drain unrelated tasks.

## Four different properties that must stay separate

| Property | Source-backed status at one worker/header response | Narrow zero-worker path |
|---|---|---|
| No live worker | Not guaranteed: standard workers persist after task completion; dedicated workers are possible. Lazy construction also means presence cannot be inferred solely from one. | No task-manager worker can originate from managerless spawn/map/bind. Other native libraries/FFI threads are outside this guarantee. |
| No runnable task | JSON response waits for direct call chain only; no global drain. IO task lifetime can outlast references. | Spawn/map/bind work completes inline; no queued manager task from these primitives. Promise/asynchronous facilities are not universally supported in this mode. |
| Locks/global allocator quiescent | No boundary contract. Empty queue is not proof all locks are unlocked. | Absence of runtime workers removes one source of concurrent mutation but is not an allocator/FFI/descriptor fork audit. |
| Cancellation safe and isolated | No response-level cancellation or fork guarantee. | Inline execution changes task cancellation behavior; child termination is a separate service mechanism requiring fidelity/lifecycle validation. |

`BaseIO.asTask` documentation (`Init/System/IO.lean:105–115`) says tasks run even when their last reference is dropped and should check cancellation manually. Implementation uses `keep_alive := true`. `task_manager.cancel:848–852` merely sets a canceled flag; it does not join a worker. `lean_io_check_canceled_core:1019–1025` checks the current managed task and otherwise returns false. In synchronous no-manager spawn there is no task-manager `run_task` scope installing the new current task, so externally canceling a managed task is not equivalent to interrupting an inline action. Cooperative task cancel therefore cannot establish a fork boundary.

No-manager execution is not universally interchangeable with every asynchronous API. `lean_io_promise_new:1052ff` requires a task manager (`lean_always_assert`); wait-any delegates directly to the manager. That is an explicit unsupported obligation for any workload reaching promises or asynchronous coordination. The old sequential header frontend avoids the inspected incremental-macro promise branch, but arbitrary extension/client paths remain unaudited. Destructing an existing manager is also not a general pause-and-snapshot protocol: its destructor marks shutdown and joins standard workers, while dedicated workers are detached by their wrapper; there is no source-backed exported universal quiescence barrier in the inspected interface.

Allocator source contains per-heap and orphan-segment mutexes, thread-local heaps and finalizers (`src/runtime/alloc.cpp:123–147,223–224,266,354–360`). Runtime object source has a global external-class mutex (`object.cpp:2336ff`); runtime IO mutex objects can be user-owned. `src/runtime/thread.cpp:49–68,117–157` initializes worker TLS, uses pthread creation/detach/join and runs finalizers on exit. Preserving environments or seeing a single process PID says nothing about ownership of these locks/TLS or external objects. No inspected source supplies atfork repair for this prepared-state contract.

## Narrow hook and explicit obligations

A technically credible source-level candidate is: launch the exact native REPL with **zero workers from its first initialization**, import through the original header interface, complete and flush a response, and expose a native branch hook outside the Lean IO evaluation stack, with separate child-owned communication. Zero uses stock synchronous primitives; branch-hook integration and descriptor handling are custom obligations. This is a candidate for later qualification, not a supported stock process-snapshot API and not an executed experiment here.

Required qualification before claiming safe reusable native process state:

1. Audit the concrete imported extension/initializer/FFI closure for thread creation, external resources and promise/wait-any requirements; source evidence here does not certify the entire selected Mathlib header.
2. Establish no live worker and no pending runnable work independently at the exact hook, then establish runtime/global allocator/foreign-lock ownership and descriptor/buffer state. Counts alone are insufficient.
3. Preserve initialization sequence and native module/version constraints; do not run initialization a second time or drop compacted regions under live references.
4. Define candidate resource behavior and cancellation. Inline task semantics can differ; a service's child kill must release the intended resources and leave parent/other candidates intact. Compare complete responses and proof completeness against original native roots rather than acceptance totals.
5. Establish original-interface behavior for any custom native adapter before attributing differences to branches. Existing step-0002 adapter mismatches are a separate unresolved prerequisite.

An alternative is prepare with no manager and only initialize a manager in each child after branching; this uses exported initialization routines but still needs a custom host, proof that no manager was already created, and workload semantic qualification. It does not inherit warmed task-manager state. No recommendation to implement either option is adopted in this node.

## Scientific impact, competing explanation and next handoff

The claim that `LEAN_NUM_THREADS=1` itself establishes a single-threaded branch boundary is contradicted by exact source. The claim that stock Lean has no synchronous initialization/task path is also contradicted: zero/no-manager behavior is real. Source does not settle whether a concrete full imported REPL header is safely branchable, or whether its synchronous execution loses useful native parallelism/changes observable behavior.

Established immutable command/proof roots, serialized snapshots and bounded warm services remain direct competitors. A zero-worker host must receive a matched zero-worker native-root control; otherwise gains or losses may be configuration effects. Process branching must demonstrate resource/cancellation/concurrency value beyond those competitors; zero-worker support alone contributes no novelty. This finding leaves the consequential Lean/SMT/GPU goal intact and does not judge the sibling dynamic-checker GPU opportunity.

Completion of this finite node: directly relevant source reviewed, stock zero-worker path identified, one-worker guarantee rejected, quiescence/cancellation/FFI gaps made explicit. Root owns scientific disposition and any next experiment. A subsequent authorized qualification would target the concrete header/initializer closure and native response boundary, with exact interface equivalence and the strongest native-root controls. No automatic experiment or new literature node is started.
