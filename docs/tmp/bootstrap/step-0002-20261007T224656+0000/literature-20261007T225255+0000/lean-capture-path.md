## Driver behavior and instrumentation boundary

### Goedel whole-proof generation

`eval/step1_inference.py` loads JSONL in order; chooses original header (fallback imports Mathlib/Aesop, maxHeartbeats 0, open declarations); constructs explanatory-comment fenced completion prompt; LLM has seed 1, max_model_len 4096, tensor_parallel_size from `--gpu`, swap_space 8. Sampling temperature 1.0, top_p .95, max_tokens 2048, n defaults32. It preserves raw outputs and prompt in full_records; regex extracts fenced code from prompt+completion; failed extraction returns literal string `None`. That string is subsequently submitted to Lean: it is a generated extraction failure and an actual verifier request, not a missing candidate. List order is dataset row then model sample order, which is not model finish order. All inference must complete before either JSON file is written: interrupted generation loses otherwise completed outputs unless generation boundary persistence is added.

`eval/step2_compile.py` submits every code through a verifier scheduler, then waits for **all** outputs before writing compilation JSON. Thus a terminated worker or hung request can prevent all final result persistence. `step3` only aggregates `complete`/`pass` and is insufficient. `verify_lean4_file` writes JSON plus CRLF blank delimiter to a tempfile, runs `[lake, exe, repl]` in Mathlib cwd with timeout300, parses stdout, maps messages and sorries, and loses native env, infotree, raw stdout/stderr and process exit code. `system_messages` stays empty throughout, so retry condition checking it is effectively inactive. Goedel memory_limit10 is **commented out** in worker; it is not an actual resource cap. Monitor runs global `killall repl --older-than310s`; this must be replaced with owned-process supervision before shared-host execution, explicitly record operational adaptation, and verify behavior. Do not launch this official monitor unmodified on shared services.

Minimal glue: durable admission event in `ProcessScheduler.submit_request` under its existing sequence lock; worker-start event immediately before every `verify_lean4_file`; persist exact UTF8 `message_str`/stdin delimiter and command/cwd before subprocess launch; capture stdout, stderr, returncode or TimeoutExpired partial buffers before JSON parsing; append full normalized wrapper result separately. Include generation output/prompt/sample ordinal before extraction. Outer step2 receives request IDs but file name duplicates samples, so unique run/task/sample/request identity is necessary. Acquisition does not need upstream copied SearchProcess modules; official eval scripts are complete entrypoints.

### DeepSeek sampling and RMaxTS

Sampling launches all generator requests then yields in request-list order, cost ordinal. Generator dynamically seeds from time modulo1000 and rank, LLM max_num_batched_tokens8192, default tokenizer/model max length, one output per request. It uses `_extra_header` + mode prompt + `_extra_prompt`, strips everything after first code fence via `post_process_output`, and stores only cleaned text. Capture raw model output, exact prompt, actual generated seed and token/finish reason before this loss. Few-shot preprocess randomly chooses 3 other validation items; choose official RL no-few-shot configuration for simple capture, or retain every selected index and RNG state.

RMaxTS creates root `sorry` verification; selects tree node using discounted reward/visitation, appends node tactic-code and optional state-comment to model conditioning, compiles concatenated header+statement+code.rstrip+tailer with ast/tactics true. Proof segmentation truncates at first error/sorry, uses feedback goal transitions for new nodes. **Failed/incomplete candidates drive the tree but are not yielded.** Completed proofs are yielded and then outer SearchProcess verifies them again without AST. Root initialization, failed internal submissions, AST extraction pass, outer success rechecks, checkpoint replay and resumed epochs must be distinguishable. `sample_info.cost` is completed inner sample count, not every native verifier call nor a universal ordering timestamp. Tree checkpoints store code lists/rewards and yielded successes; they do not replace event capture.

Minimal glue shares Goedel admission and actual subprocess instrumentation, with metadata propagated as a sidecar from `Proof._update_full_code`/`ProofSummarizer.analyze` and outer SearchProcess: task/run/root ID, parent node/selected exact code-prefix, call role root/internal/outer, sample and generator-request identity. Log full native response before `lean4_parser`; AST postprocessing exceptions otherwise overwrite valid main-response content with generic failure. Do not add metadata keys to kwargs passed to `verify_lean4_file` because it accepts a fixed argument list.

The pinned fork's `REPL.Main.runCommand` first calls `IO.processInput`; `ast=true` calls `extractAST s.cmd`, whose complete source independently parses header, `processHeader`, and `IO.processCommands`. For native work accounting instrument these two Lean entrypoints separately or preserve substage traces in a declared build; transport capture guarantees every external request, not visibility of every internal elaboration. A warm service that reuses first-pass imports but still performs AST fresh imports cannot be credited with eliminating all preparation. Changing AST generation to reuse the first info tree would change the official capture producer and is an ablation/implementation decision, not read-only acquisition.

DeepSeek resource limit10GB is active RLIMIT_AS per worker. Verifier concurrency64 and search256 default need memory/CPU sizing. Default sampling128 and RMaxTS6400*16 runs are published policy settings, not minimum bootstrap requirement. A finite acquisition config with fewer repeats/samples/concurrent slots is a declared workload policy variant; do not label its pass rate a reproduction of the paper. Scheduler close discards queue via all_tasks_done; missing responses can cause indefinite output waits. Monitor has same global killall issue as Goedel.

### DSP+ workflow and inside-Lean tactic candidates

Workflow schedules attempts outermost then dataset; process start order is not actual submission order. Stops a task when finished.txt exists; checks of this file race with concurrently running attempts. Draft JSON is removed after sketch JSON, sketch JSON removed after prove JSON; only cumulative selected content survives. Error masking verifies **every transformed sketch**, ignores unsolved-goal errors, comments/removes lines and replaces children with sorry. `remove_error_line` submits another placeholder proof; `send_request` submits bfsaesopLoop/BFS source; strict retry (not default) contains a missing `bfs_list` argument on second call and would require correction if enabled. Final `_prove.json` retains final response, not all masking/proving tries. The persistent verifier starts setup command and chooses env0 for every job (last_env never advances). It replaces literal shared-header text with a comment before transport, strips pre-JSON output, discards native env and AST, and restarts after360 seconds, timeouts/EOF/errors. **Record original source AND transformed command plus setup-source/environment-generation ID.** Retry and setup imports are actual native invocations; age-based MemoryError before send is a lifecycle event, not a Lean rejection. Timeout branch restarts and leaves timed-out result; some other errors retry at most2, age restart path not governed by attempt increment.

Python queue and sendline instrumentation captures every sketch/proof command and retry but **cannot capture each BFS tactic trial**: those happen inside one Lean command. Custom `Aesop.RuleTac.tacGenImpl` saves initial Meta state, obtains suggestions, restores state per suggestion, parses and `evalTactic`s each one, rejects proofs with sorry, accumulates failures, returns successful applications. If at least one succeeds, the errors are not part of returned RuleTacOutput. `LeanCopilot.tacGen` conditions on pretty-printed goal, filters self references and aesop; external model uses curl POST to local /generate. Python API deduplicates/samples suggestions by logprob before returning them. API generation logging alone therefore records suggestions, not which native trials ran or their results.

For a complete DSP search trace, additionally instrument generated-tactic loop **before parsing** and around evalTactic/catch, preserving syntax string, full native saved-state/context identity (not only pretty goal), score, parent goal/search-node, order, post-goals, native exception, sorry result, and cancellation. Use generic `Aesop.Search.Expansion.Basic.runRuleTac` for regular rule trials when claiming every search rule rather than only model suggestions; keep this boundary distinction explicit. Exact replayable context can be obtained from native state snapshot plus environment identity or deterministic original setup/parent path; pretty goal alone is insufficient. Instrument setup `start_lean4_server` too. This involves pinned Lean dependency hooks, more than Goedel/DeepSeek transport glue; source-native feasibility is verified but full implementation/replay not executed.

## Crash/cancellation and completeness contract

Admission log proves an intended request; transport-start proves an actual attempted native call. A queue item cancelled before transport is not a verifier submission. Each retry has a distinct invocation ID under one logical request; each worker/process generation has its own sequential counter. Root-level global scheduler sequence records admission order; per-worker transport order and timestamps record execution partial order. Never fabricate total chronological completion order by JSON list or sample cost.

Persist append-before-submit/send (flush/fsync under explicit durability policy), append full response/exception afterwards, and store producer process termination/cancellation events in a supervisor-owned log. Reconcile admitted/started/responded sets after shutdown; unexplained started-without-result is interrupted/unknown, not rejected. Signal intent alone does not establish native cancellation acknowledgement. Capture raw partial output, exit status/signal and timeout/OOM/supervisor cause when knowable. Record not-run generation/extraction failures separately. Full native result is raw wire output plus requested flags/context/toolchain; `complete` boolean and wrapper pass are only producer interpretations. Capture does not itself prove kernel acceptance or theorem integrity, especially Goedel's generated whole code can alter original statement/options; keep original problem and source checks as later validity qualification without silently filtering actual traffic.

## Matching-version warm and snapshot competitors

Pinned 4.9 fork and4.17 community REPL **already** implement env backtracking, ProofSnapshot state IDs, command/proof pickle/unpickle. `runCommand` restores exact Command.State from selected env ID; logical roots are established prior mechanisms. `CommandSnapshot.pickle` serializes imports, constants.map2, compact command state and context; unpickle imports modules anew and replays constants, restores scoped namespaces. It drops closures/caches/messages/info/trace state. Proof pickle stores meta/term/tactic state but compact core excludes environment caches/messages/info and context closures. `Util.Pickle` uses saveModuleData/readModuleData, returns CompactedRegion; freeing while references remain is unsafe, ignoring it leaks. Main unpickle currently ignores region handle; bounded worker replacement needed.

For exact old-version numerical comparison, mandatory runnable primitive families are (1) bounded persistent pinned REPL with header/prefix roots and common exact-result cache, env0 branch per candidate, worker retirement; (2) native pinned command/proof snapshot pickle/unpickle with all import reload/cache and resource costs included. DSP already uses bounded-age warm env0 and custom search state save/restore; do not call it fresh-only. Goedel/DeepSeek subprocess-per-request official path is a native control, not strongest warm baseline. Existing Kimina current version is an architectural precedent but cannot be assumed binary compatible with Lean4.9; same-version service lifecycle glue or a genuinely old-compatible release must be qualified. Roots currently append cmd/proof arrays; bounded reset/recycle is required, not unbounded accumulating warm memory strawman. Native pickle is not full runtime history preservation; qualify outcome/context extensions before admission.

Lean4.32 executable header/full snapshots and Snapshot-DSP patched4.25 are **not available in these frozen versions** by merely setting a flag. A newer-version migration must revalidate all benchmark source, tactics/library dependencies and native results, and be a separate corpus/version condition. Do not use4.32 speed as matching old candidate reference or silently upgrade. Strongest matching old native snapshot mechanism exists now, so unavailable newer artifact does not justify omitting snapshot comparison.
