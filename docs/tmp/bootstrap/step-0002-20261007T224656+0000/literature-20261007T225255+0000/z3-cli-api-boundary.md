## Decision

**The source establishes a real construction-order and manager-ownership difference, but does not definitively attribute the five statuses to it.** The API eagerly creates its manager and solver before reading the stream's options; CLI installs the same strategic factory on an initially manager-less context and creates the manager/solver later. Both use the same command checker/resource-limit implementation and the same strategic solver factory. Thus “the API always chooses an incremental default solver whereas the CLI chooses a different solver” is unsupported. Simply subtracting prefix resource counts is also unsupported: the limit is relative to the current count at each scoped push.

The finding changes the next feasible qualification target: a version-pinned CLI frontend hook retaining its own command context and exact parser/manager/solver construction is credible; the public evaluator remains unqualified. It does not establish that branching is safe or useful, that a repaired API would match, or that the native mechanism beats established reuse.
