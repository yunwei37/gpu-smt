## Question and decision

RQ1 asks how much *expensive native preparation* independent real candidates can share. RQ3 compares complete equal-resource serving with established reuse. The decisive unresolved distinction is whether branch disposal can preserve the same consequential native preparation that strong logical snapshots already preserve, without importing previous candidate history and without losing the benefit to private page mutation and lifecycle overhead. Merely retaining more header strings or choosing another finite worker lifetime does not settle it.

The current first-header-only service already shares the dominant Mathlib import state across other ProofNet headers. It does **not** preserve any completed command snapshots in disposable branches. Strong warm and snapshot competitors demonstrably do. A new exact-header parent can fix this preparation-depth asymmetry, but the current source/data does not establish that the missing opens/options/short definitions are expensive enough to overcome per-candidate branch cost. The root should distinguish that correction from a contribution. The larger preparation-depth/history/resource discriminator remains compatible with the full original goal, including main formal tasks, supporting full-module edits, and SMT.
