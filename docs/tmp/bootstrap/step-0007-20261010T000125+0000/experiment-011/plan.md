# Experiment011: real warm Lean arithmetic against native exact search and selection

## Research question and paper-value admission

RQ4 verbatim: **After preparation reuse, when does heterogeneous execution improve complete verification over the strongest measured CPU path?**

This supporting experiment resolves a necessary route decision, not the whole RQ: on the original failure-inclusive formal candidate streams, how much complete warm verification work remains in arithmetic certificate search after native exact CPU search and numerical hypothesis selection? Farkas already supplies these mechanisms on Lean4.31; its author-reported solved-proof corpus does not answer the question for our unchanged4.9 generated attempts. Largest credible story unlocked is a source-native heterogeneous verifier evaluated against competent CPU arithmetic, or a measured reason to choose another expensive checker operation. Neither a faster CPU oracle nor a component GPU LP rate is our novelty.

Positive CPU gains plus substantial residual costly certificate demand select a full-boundary GPU arithmetic experiment. Tiny residual demand or dominant preprocessing/reconstruction selects frontend/dynamic checking instead. Feedback divergence, unsupported port or incomplete cohorts remain inconclusive and cannot be counted as a CPU/GPU win. This is supporting, not headline evidence and not an independently sufficient GPU conclusion. The best alternative is another native process shutdown/fork attempt; its present supported full-depth boundary has failed admission, while a repeated source806 profile would add no corpus evidence. A closure-based kernel route remains open if arithmetic is unimportant.

## Comparison and hypothesis

Expected: a native exact oracle alone may remove interpreted arithmetic search, while numerical selection can also avoid expensive proof-term preprocessing. Strong competing explanation: these public CPU techniques leave too little large ready work to justify GPU transport/search. Published4.31 numbers cannot be transplanted as our effects.

One main competitor family is the same-version original stock arithmetic path inside competent full native snapshots. The Farkas numerical-selection path is the strongest relevant CPU alternative whose measured residual costs are required before any device claim. Oracle-only is a component ablation, not another main baseline. A matched run is necessary because versions, candidate failures and code composition differ from published solved-proof data. If the CPU alternatives match or win, GPU arithmetic must beat their complete boundary or be rejected for this workload; CPU gains alone never establish novelty.

All arms use identical candidate bytes, original normal checking/kernel finalization, full native reuse, original300s policy, one ordinary worker and the collector's existing default retirement256. This defaults-based retirement is fixed identically, not tuned here or claimed optimal. The separate E002 warm512 policy is not changed. No result cache or accepted-only filtering is introduced. Preserve stock explicit oracle/config arguments. Numerical selection remains untrusted; every returned proof is constructed/checked by stock Lean. Port failures restore saved tactic state and fall back to the original complete call; any difference from upstream fallback handling is declared as compatibility behavior, not official unmodified execution.
