## Native concurrency and lifetime audit

The initial implementation exposed two real defects: the dedicated count reached zero before finalizers, allowing ordinary workers to disappear early; and `spawn_worker` refused work during shutdown even if a dedicated/finalizer path enqueued an ordinary dependency. In build4 `owned-object.cpp:585-590`, historical handle storage and runnable ordinary-loop count are separate. `enqueue_core` selects worker capacity using the runnable count, and `spawn_worker:650-674` may start queued work while teardown is active. Slot increment/loop exit occur under the same manager mutex as queue management. Dedicated handles are retained at `677-688`; decrement/notification occurs in the added completion callback. `owned-thread.cpp:61-69` destroys the main closure and runs both Lean finalizer phases before invoking this callback. The original lthread constructor remains at `153`, alongside the added overload; the public lthread object representation remains unchanged.

The destructor at `owned-object.cpp:784-800` swaps both handle registries under the manager mutex and joins outside it. This avoids joining while blocking a worker/finalizer on that mutex and avoids iteration over a concurrently mutated registry. Threads created by a joined batch's callbacks remain in the member registries for a following batch. Since each batch is joined before another empty-registry decision, owned callbacks from that batch cannot register work after the destructor's terminal empty check. Actual pthread joins also cover Linux stack-guard cleanup after `thread_main` (`stack_overflow.cpp:92-96`), rather than treating the completion counter as OS termination.

Ordinary workers can retire at zero dedicated count before their own finalizers finish, but any newly queued ordinary work can create a replacement loop and its retained handle is joined in another batch. The source-native successful-return argument therefore does not require ordinary finalizers to be no-ops. All spawn/registry mutation paths inspected are reached with the manager mutex held. I found no remaining concrete late-enqueue, handle-ownership or join-under-lock defect in this revised successful-return path.
