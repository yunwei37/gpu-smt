# Experiment007 plan — complete native Lean resource comparison

## Research question and admission

**RQ3: How does prepared-state branching change end-to-end latency, throughput and memory at equal resources compared with established warm-session reuse?**

Specific uncertainty: on actual attempted Lean edits, does disposable process execution from fully completed native snapshots offer a useful CPU/memory tradeoff over concurrent native logical snapshot reuse, after each candidate receives complete original-source/declaration finalization? This is a BOOTSTRAP decisive mechanism/resource discriminator, not finalRQ3 coverage or implemented production service.

Largest credible story unlocked: native execution-history/lifetime separation survives a strong supported logical reuse path on complete verification and changes a consequential parallel resource frontier. Strongest reject argument: native immutable snapshots plus bounded concurrent workers/cache already capture useful preparation with less cost than COW. Previous fixtures, stage profiles, SMTprefix qualification, GPUmetadata and released menu timers cannot reanalyze this missing relation. LiteralSMT full-flush sharing is namespace-confounded, making additional such qualification dominated. New realLean candidates/source-native complete checking and matched CPU-resource comparisons add independent evidence. Prior literature already establishes cold/warm savings and snapshot mechanisms; do not rerun a weak cold headline. A positive result grounds the specific implementation/placement opportunity; dominance by native logical reuse rejects this candidate resource advantage at this boundary, not the entire Lean/SMT/GPU thesis. Mixed speed/memory tradeoff motivates a concrete cost-sensitive retention/placement comparison beforefreeze. Unsafe/incomplete/native-parity failures invalidate a speedclaim rather than becoming a win. The better alternative is deeper dynamic native work/heterogeneous complete checking; this CPU experiment is runnable without the stillPending5090 model allocation and first determines whether claimed preparation advantage survives native competitors.

## Expected and alternative outcomes

Process branches preserve an independent runtime/candidate lifetime and may reduce shared mutable runtime/reference-count contention at parallelism, but add manager restart/fork/COW mutation/teardown. Expected answer is conditional, not presupposed speedup: existing native logical reuse may win. Contradictory local result is logical reuse matching/dominating fork across tested CPU scales and observed fleet memory, or any protected response mismatch. A memory increase is a tradeoff, not automatically an invalid run; wrong/incomplete checking or unfair resource composition is invalid. No necessary universal thesis prediction is tested here.

## Comparison and implementation

Proposed **fork**: exact official fullnative original snapshots are completed and checked. A DECLARED native runtime extension intercepts initialize_libuv using the linker --wrap flag. It retains an owned joinable pthread instead of stock's detached event thread, preserving native event-loop initialization, stack size/guard, thread initialization, inherited heartbeat and TLS finalization. The owned loop uses the source-native loop body with its outer aliveness predicate moved UNDER the existing mutex, after requester waiters settle; this prevents observing a temporaryunref as an exit signal. This synchronization change is explicit in both methods. At the boundary it locks the native global loop, uv_walk refuses every handle except the stock async handle, temporarily unrefs that handle to require uv_loop_alive==0 (no other active requests/closing work), then closes the sole handle with a plain completion callback and joins its owned event thread including TLS cleanup WHILE taskmanager remains available. Afterjoin it drains any remaining close callback via UV_RUN_NOWAIT and requires closurecompletion, no handles and no alive work before reusing asyncstorage. It next stops/joins taskmanager, preserves the own-live-thread count1 guard, forks, reinitializes manager, invokes official uv_loop_fork in the CHILD before any childloop use, reinitializes the async handle and starts an owned event thread in both parent/child before returning to Lean. Unexpected UV handles/requests, transient dedicated or unknown extra threads, fork/restart failures refuse this path without credited fallback. This is a specialized runtime extension for the observed idle-loop boundary, NOT an unmodified stock runtime or a general safe-fork certificate. No Lean allocation/destruction/callback while manager absent. Child owns new frontend snapshot/cancellation work, completes source check and writes requested result, then exits; parent reaps. At mostP active branches. Any guard/initialization/child/IO failure is retained as unsupported/operationalfailure; no silent fallback credited tofork. One-TIDguard is engagement evidence, not universal fork safety; importedplugins/FFI/allocator/descriptors remain exact-workload qualification limits. Actualdistribution usesmimalloc, unpatched native-runtime helpers; thinFFI source explicit.

One main baseline **logical**: SAME executable with the joinable-event-thread runtime extension (normal loop stays live; no stop/fork/restart action), same official fullsnapshot roots, native incremental source processor, bounded concurrent independent logical calls. StockCLI remains the unmodified behavior control. No performance difference is credited to different kernel/frontend/check options or missing event loop. Uses native dedicated outer tasks to avoid blocking all normal frontend worker threads; P normal taskworkers and up toP active outer calls. It does not accumulate every completed candidate state. Complete snapshot trees are settled before preparing reuse; old snapshot cancellation references can be touched by the official reuse algorithm, so actual full-response/fingerprint parity is a hard comparison condition. This path represents the strongest directly source-supported snapshot sharing in4.21, not a custom goal-onlyREPL.
