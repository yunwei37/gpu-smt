## Declared claims, questions and coverage boundary

C1/RQ1: actual public Lean attempts, including unsuccessful attempts, can expose expensive shared preparation. Threats are successful-proof selection, deduplication, goal-only state loss, reconstructed or mutated examples, absent native inputs, missing versions and absent original ordering.

C2/RQ2: independent native execution can preserve outcomes and isolate lifetimes. Threats are printed goals substituted for original metavariable/local-instance state, diagnostic censorship, admissions, resource limits, timeout classification, and incomplete original-declaration finalization.

C3/RQ3: preparation sharing may improve the equal-resource frontier over competent native reuse. Threats are already-existing tactic-state restoration, command checkpoints, persistent workers, result caching, and workloads that artificially inflate cold imports or fan-out. No novelty for failure collection, save/restore, or process branching is claimed.

Finite source branches: (A) publicly released RL rollouts; (B) released whole-proof evaluation completion traces; (C) released complete tactic-candidate pools and optimizer histories; (D) artifact claims contradicted by actual repository trees. Primary papers, official repositories, HF cards/API/sample rows and actual archive members are required. Completion means each branch has a verified inclusion/exclusion decision and one concrete experiment handoff; it does not mean proving no other dataset exists.

### Direct native reuse already present in official source

[Pinned LeanPolish.lean](https://github.com/paulinebourigault/leanpolish/blob/70cda81a15cca1f805885df197361102f0123cbb/leanpolish/LeanPolish.lean) was read at the relevant complete functions:

- `runTacticString`, lines125–192, parses the original tactic, saves TermElabM state, runs the tactic in the original local context/local instances, checks remaining goals, errors, sorry and metavariable leakage, then restores state after success and exceptions. This is an existing competent native logical-state baseline.
- `checkAutomationsAll`, lines420–473, executes the declared menu from `ti.mctxBefore`; guard failures are recorded as skipped. Four expensive menu entries receive cooperative5000ms timeouts normally; `--menu-timeout-all` changes that policy for all entries. This flag must match each actual run.
- Initial source elaboration, lines2123–2160, saves Command.State and parser position at every command. Later re-verification resumes after unchanged commands. Worker mode at lines959–962 shares imports across files. These mechanisms directly threaten any claimed advantage based only on repeated import or unchanged-preamble elimination.
- Pool emission includes the original spans and outcomes at detection time before overlap/whole-file selection. exact? fallback and later combined verification still execute outside the15-entry pool. Therefore “complete pool” means complete declared menu records for visited sites, not complete historical native-call traffic.

[Official complete-menu protocol](https://github.com/paulinebourigault/leanpolish/blob/70cda81a15cca1f805885df197361102f0123cbb/experiments/complete_menu/README.md) provides native driver commands and rawlog hooks. Actual archived axiom_r2/A2 raw log says `--complete-menu, --menu-timeout-all`, shared import setup10491ms, source elaboration27152ms and a fold-budget exhaustion skipping remaining automation. Thus visited-site selection and partial runs remain visible. No invisible remaining site may be invented.

[Independent verifier](https://github.com/paulinebourigault/leanpolish/blob/70cda81a15cca1f805885df197361102f0123cbb/leanpolish/verify_pair.py) checks source hash/span and splices an edit for fresh file compilation. This is useful for source qualification and complete-file behavior, but substituting this full-file edit check for historical same-state tactic calls would change the workload boundary. Printed goal_state cannot reconstruct actual metavariable identities, local-instance state or runtime objects. Native re-elaboration of the released original file and original InfoTree context is required for tactic-level experiments.

## Follow-up: exact pool boundary and full-declaration verification (root-requested source discriminator)

Root requested a new, consequential boundary audit after independently retaining pinned source. This appendix supersedes any interpretation above that pool `valid` means a complete original proof has been kernel-checked. It does not change the RQs, inputs or root plan. The same pinned public `LeanPolish.lean`, `leanpolish.py` and `verify_pair.py` were reread at complete relevant functions; no backend was run.

### What happens before each pool entry is emitted

`runTacticString` (LeanPolish.lean125–192) parses a tactic and executes `Tactic.run mainGoal (evalTactic stx)` at142. Its explicit success predicate at164 is: no returned goals, no new error messages, no detected assignments leaking into earlier metavariables, and no literal sorryAx found in the main goal's recorded assignment. It instantiates the goal type for rendering and counts assignments. It then restores the saved TermElabM state at172; the exception path restores at179. There is **no explicit per-menu-candidate `Meta.check`, original declaration assembly, `addDecl`, or kernel declaration check** in this function or in `checkAutomationsAll`420–473. Individual tactics may internally perform checks; that fact cannot establish that every successful menu result passes full original declaration finalization. The helper discards the candidate's state rather than returning its proof term as an original declaration ready for checking.

The emitter at2520–2527 maps `!o.valid` directly to the string `rejected_kernel` after the skipped/chosen/timeout cases. It does not ask which subsystem rejected the attempt. Parse failures, tactic exceptions, remaining goals, detected sorry or metavariable leakage can therefore all receive that label. Quality and length failures have separate labels, but `rejected_kernel` is still a broad pipeline label rather than evidence of a literal kernel rejection. The four failed B6 entries verified above establish actual native tactic failures; their label does not upgrade them to kernel-checking events.

`[MENU_POOL]` is emitted at2552–2565 immediately after collecting menu outcomes and rendering the original goal. This precedes exact? fallback at2575–2588, candidate collection at2626–2638, overlap selection and full modified-source verification. No subsequent full-file result modifies `MenuOutcome.valid` inside this execution. Published derived `accepted_after_verify` is a later selected-edit/site attribute; it is not a certificate for every `valid_not_chosen` alternative. In particular, a valid-but-unselected candidate has not thereby been individually spliced into and checked as the original whole declaration.

The only explicit `Meta.check abstractedProof` calls in the inspected Lean source are3178 and3208 in the later local-fact anti-unification phase. They do not lie on the ordinary15-menu candidate execution path and cannot establish its per-candidate verification completeness.

### Where original source is re-elaborated later

Phase1 applies the selected nonoverlapping candidate set to original source at2771–2775 and calls `verifyTextIncremental` at2777. The latter (1565–1622) restores the last pre-edit Command.State, parses every subsequent command and calls `Command.elabCommand` at1612. Thus modified original declarations enter ordinary command elaboration instead of merely closing a saved goal. Full fallback `verifyText`1512–1549 likewise parses source commands and calls `Command.elabCommand`1539 from the import environment. This is a distinct, later source/declaration boundary; it is applied to selected joint edits, not each recorded menu attempt. The helpers contain no separate explicit await/inspection of asynchronous declaration tasks or returned finalized declaration certificate. Root's exact Lean4.21 native source/runtime qualification must establish finalization and completion at this boundary before admitting it as the complete verifier authority.

`errors.isEmpty` becomes `verified := true` at2779–2783; if the main loop fails, the code runs full `verifyText` at2852. L2 joint/per-group re-verification, cleanup re-verification and conditional final checks also use these helpers. `TRAINING_PAIR` emission occurs only later at3793–3838 for surviving active edits when `hasTacticChanges` is true. Its accepted label and attached failed siblings therefore have different timing/scope from the earlier menu pools.

A concrete qualification risk: both `verifyText` and `verifyTextIncremental` set a local `hitCrash` flag on an `.error` returned by command elaboration, but then return only error-severity messages from the retained Command.State. They do not explicitly push a crash record. If an exception produces no retained message, the empty-error test alone could misclassify that path. This is a source-level possibility, not an observed runtime failure. Likewise these helpers collect errors but do not independently reject sorry warnings or audit the axioms of a final declaration. Goal-helper checks cannot be generalized to a whole-file admissions guarantee.

### Independent fresh-process checks and their limits

The official Python driver's `_postverify_shortened` (leanpolish.py219–243) runs original `lake env lean` on the **combined shortened file**, checks process return code and error text, and is bypassable by `LEANPOLISH_SKIP_POSTVERIFY=1`. `_postverify_with_bisect`419–452 recovers a compiling subset or quarantines the output on a failing postcheck. This is useful original-executable finalization evidence for the retained combined result when actually enabled and completed. It is neither a per-menu-candidate check nor an absolute admissions check: the helper does not reject sorry warnings itself. Archived exact environment/configuration must establish that the bypass was not used before relying on this gate.

The independent `verify_pair.py` per-row checker131–240 does splice one released edit into its original full source and invoke a fresh original `lake env lean`; it records exit/error/timeout and detects sorry warnings. It rejects sorry only when the candidate has them and the baseline did not (`cand_has_sorry and not base_has_sorry` at233), rather than requiring both files to be admission-free. It has strict source hash/span gates and a baseline compilation gate. Its pass can support a specifically executed full-file edit check under the qualified baseline policy; the **existence of this tool is not evidence that every menu alternative in the archives went through it**. Applying it now would create new per-alternative full-source measurements and must be labeled that way, rather than claiming a replay of historical native tactic calls.

### Truthful admission consequence

LeanPolish remains a verified publicly released **actual tactic-attempt source** and a direct strong native-reuse competitor. Its complete-menu records are not already a complete full-proof verification corpus. Complete verification serving would need original native construction plus the appropriate original declaration/file checking stage, preserving failed tactic outcomes and later whole-source outcomes separately. Measuring only save/restore and goal closure cannot answer full verification RQ2/RQ3. Conversely, injecting a fresh full-file check for each historical tactic attempt without declaring the changed boundary would also be invalid. Root should retain the promising asset and the conditional qualification handoff, with this sharper native-boundary limitation and all later verification/failure/cancellation costs visible.
