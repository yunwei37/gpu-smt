## Cache invariants and lifecycle findings

1. **No object-size or field-offset ABI change.** LeanRef still contains the ordinary lean_object header and value pointer. Native lean_st_mk_ref initializes m_other to zero, then invokes the creation hook before returning/publishing the ref. m_other is an existing eight-bit field; its native documented uses are constructor arity and scalar-array element size, not ref size. The cache does not alter those other object kinds. Generic size/deallocation uses m_cs_sz/native allocation information, not ref m_other.

2. **Owner tags are reserved, not truncated full IDs.** Each enabled Context reserves a currently unused nonzero tag under the registry mutex. Every tagged ref creation additionally increments tag_uses[tag] and retains both its full ID and tag in the owners record. Context exit releases its reservation only after admitted tasks/scopes finish and held clones/originals are decremented. A surviving owned ref keeps a tag reserved after its originating context is gone. Therefore a different live context cannot acquire the same nonzero tag merely because an earlier context ended. Tagged-ref retirement decrements the recorded tag before erasing its owner record. Creation/allocation and reservation/deallocation bookkeeping share one registry mutex.

3. **Exhaustion does not cap admitted work.** If all 255 cache slots are reserved, owner_tag remains zero; owned_here performs the previous full-ID registry lookup. Disabled contexts also retain the full-ID behavior and bypass the resolver as before. No wait/reject/quota follows from cache capacity. Escaped persistent refs may retain slots indefinitely and reduce future fast-path coverage; that is a performance/coverage limitation, not a concurrency cap.

4. **The fast read has a publication argument.** Ref m_other is assigned before the new ref is returned and is not modified on that same live heap identity later. Native lean_mark_mt changes m_rc and visits child values without rewriting m_other. Normal native cross-thread publication thus carries the already initialized owner byte. Other job refs fail the tag comparison and follow the private-version map. Prepared/root refs have tag zero and also take that path. This reasoning assumes the normal native ownership/publication contract, not extension code publishing incompletely initialized objects or manually mutating headers.

5. **Bypass clones are intentionally untagged.** The hook returns during resolver Bypass; the native constructor has already initialized their header to zero. They are found via ctx->refs when the original identity is accessed again. No tag counter is claimed for a bypass-created clone. Its eventual ordinary free can find no owner record and return harmlessly. This is the pre-existing clone ownership model and does not give another context the creator's tag.

6. **Deletion does not reread a rewritten header.** Native deletion lists can overwrite RC/size bytes before lean_del_core visits a ref; the hook uses retained Owner.tag, not the object's current bytes. The hook runs before the underlying ref allocation is freed. A context reservation prevents reuse during its own held-object cleanup; if the last context/ref reservation is removed, the deleted ref is already unreachable under the ordinary native RC contract. Address reuse goes through fresh native header initialization and a new owner record.

7. **Both compaction boundaries clear copied ownership.** copy_object copies the old header; the new insert_ref hunk resets the copied object's m_other to zero before its offset object enters max-sharing and is serialized. fix_ref resets the loaded object's byte before publishing the loaded compacted region. Neither action clears the original tracked heap object's tag or decrements its reservation: the original identity is unchanged. Compacted refs are persistent region identities, not hook-created candidate-owned heap refs, and correctly miss the nonzero owner fast path. Both hunks must be present in any newly linked candidate runtime; changing only the helper library would leave the copied-tag hazard.

8. **Ordinary sharing and pointer equality do not introduce new identities.** sharecommon traversal deliberately skips mutable refs and its quick path returns the same ref after RC increment. lean_st_ref_ptr_eq compares actual ref addresses. Neither operation needs tag transfer or an extra reservation. The ordinary sharing exclusion is narrower than claiming all unsafe low-level Object operations ignore the byte.

## Limitations and minimal follow-through

- The low-level unsafe ShareCommon.Object.eq/hash exports directly include m_other when called on arbitrary non-scalar objects. Direct unsafe calls on refs can therefore observe different structural hash/equality values after tagging. Ordinary sharing never inserts refs into that structural set, and these unsafe primitives are not the native ref identity contract. Do not claim byte-for-byte header transparency or arbitrary unsafe-extension compatibility. No evidence here shows those calls are used on refs by the formal workload; this is a stated support limit, not a reason to launch a new correctness campaign.
- Raw external deallocation/header copying/manual LeanRef allocation outside the hooked native paths remains unqualified. The full-ID registry already depends on supported allocation/retirement hooks; the cache does not repair arbitrary FFI behavior.
- Full uint64 ID/tag-use counter wrap is theoretically possible and unhandled; it is not introduced as a practical admission limit or tested claim. Ordinary source-level lifetimes and normal exact accounting are the reasoning boundary.
- This removes the global ownership-map lock only from resolver accesses with an available tag. Creation/free still take the registry mutex; ref_ops still performs one atomic increment per enabled access; foreign/prepared refs still take ctx->mutex and use private versions. Source inspection cannot establish a speedup or predict whole verification wall time.
