## Counting and context switches

The source contains four runtime assignments to current after its TLS initialization. task_enter flushes the outgoing current before saving/switching it (175-180); task_leave flushes the installed context before restoring saved (182-186); branch_end checks the handle, flushes the root context, then clears current (214-218). branch_begin only installs a context when current is null (197-211). Initially both local counts are zero; every path that can return current to null already flushes and clears them, and increments occur only after the resolver's current/enabled/bypass checks. Consequently begin does not inherit counts from an earlier completed context under these actual entry points.

Nested task scopes also preserve attribution. Enter flushes the outer context and resets the TLS accumulators, the nested task counts into its installed context, leave flushes it and resets before restoring the outer one. Reentering the same context merely divides its total into additional sums. Scope switches to an unregistered task/null context flush the old context and do not count disabled/null accesses. Bypass work remains excluded as in source-before.cpp. Each TLS counter is touched by one native thread; Context totals remain atomics shared by flushes from different threads. No new lock is added by flush_local_ops.

A task flushes before decrementing its admitted scope count and notifying the owner. Root branch_end flushes before waiting for both tasks and scopes to reach zero. The native execution RAII scope includes lean_apply_1 and its cleanup before leaving; the earlier deactivate_task_core scope retains the context across dependent/closure destruction and native relocking. Context remains live during each flush by the same root/admitted-scope lifetime assumptions already required by the original resolver. The flush is sequenced before scope release under ctx->mutex; the waiting owner acquires that mutex before inspecting the drained state. Thus final counters are not read before the admitted final flushes. The atomics' relaxed additions need no new lock or stronger per-access ordering for this end-of-branch aggregate.

The visible measurement change is deliberate batching: Context.ref_ops/thunk_ops can lag actual work while a thread remains in its current scope. They are no longer exact mid-scope progress counters. At a normal fully drained branch end, the same admitted resolver entries are summed; no work should be inferred absent merely from a temporarily unchanged total. Abnormal process _Exit/crash never produces a normal complete branch aggregate; the old per-access atoms also could not make such a failed process a completed observation. Integer overflow remains the pre-existing finite-counter limitation, not a new admission cap.

## Single-entry version cache and lifetime

last_ref/last_thunk are per-thread and store a full unique Context.id, the original identity and its private version pointer (51-59). Lookup tests the currently live ctx ID first and then the caller-provided original identity (117,135). It does not dereference a prior cached original/value unless both comparisons match. Each remember call is reached only after finding an already-created map entry or after the new original and clone have been added to ctx->held and the private map (119,126-129,137,149-152). Original and clone therefore remain alive throughout that context, independently of caller references. Context maps do not replace/remove their values before full drain. A hit cannot select a different version of the same original later in that context because the authoritative mapping is stable.

Caches can retain stale pointer representations after context destruction, but a later context has a different full ID even if an allocator reuses the Context or Lean object addresses. Returning from a nested context to the outer one may evict the useful cache entry; it cannot cause a false hit. Hits on a still-live outer context after a same-context nested scope remain valid for the same held objects. The theoretical full uint64 context-ID wrap is inherited from the registry's ID mechanism; this source review does not claim protection against that wrap or arbitrary fabricated object identities.

The cache is populated under the existing per-context mutex. A different thread builds its own cache only after finding the map under that mutex. No shared map is read without its lock on a miss. Hits read only immutable TLS metadata and the already-held private pointer, so there is no new map race. Private ref clones are MT-promoted as before; the cache changes resolution lookup, not the native atomic ref operation on the returned clone. Thunk hits return the same retained clone that the map would return; its native evaluation/exchange behavior remains unchanged. Already-evaluated original thunks return without being remembered, avoiding a cache entry whose original lacks the held lifetime.
