# Experiment plan: RQ4 native argument-cost admission

Status: closed without execution after fresh plan review. The original proposal below is retained; see plan-review.md and disposition.md. No new native capture or GPU provider has run.

## Research question

RQ4 verbatim: After preparation reuse, when does heterogeneous execution improve complete verification over the strongest measured CPU path?

Specific uncertainty: how much observed native Meta cost is actually spent inside different, closed argument comparisons that the existing native argument loop reaches after parent quick/cache/reduction shortcuts? The prior entry-level flags do not identify those child comparisons. This is an optimistic cost opportunity, not evidence of simultaneous readiness, a GPU algorithm or saved wall time.

## Paper-value admission

Planned role: supporting. The possible paper consequence is retaining or closing a materially broader closed-argument offload hypothesis within the heterogeneous execution experiment, before implementing another provider. A small measured surviving cost closes this target; a large cost warrants evaluating a concrete independently ready algorithm, but does not by itself admit a GPU backend or establish novelty. Mixed/incomplete/strongly perturbed coverage remains inconclusive.

The E032 full user-CPU sample identifies about 35% inclusive Meta defeq and 23.16% inclusive argument comparison, whose nested regions overlap. E033 provides outer flag CPU and all-call counts over all 29,750 inputs, but only outermost wrapped-call timers. Its raw data have no actual argument-call-site tag or child CPU intervals, so they cannot recover this fraction. The complete native6 GPU comparison closes its scalar beta/zeta constructor; it does not measure this post-shortcut child population.

Strongest rejection argument: this is another costly profiler of a narrow route already unlikely to survive GPU overhead, while the paper still lacks a differentiated prepared-state system and multi-context service evidence. The proposed run has value only if the missing child-cost evidence could actually change implementation investment; if the fresh reviewer finds the current evidence already sufficient to close it or a higher-value runnable experiment dominates, reject this proposal without executing it.

Best alternative: a differentiated candidate-body/prepared-state mechanism on real multi-context candidate traffic. No such new mechanism or suitable matched real multi-context traffic is presently established; merely reshuffling the single-header cache repeats prior work. This proposal may be the most immediate way to settle the remaining cost prerequisite for the explicit user request to quantify useful defeq work before a GPU backend. This relative-value claim is for review, not an assumed scientific pass.

## Comparison and metrics

The competent compiled native original is the sole same-path control, not an intentionally cold baseline. Existing full E032/E033 captures supply context, not matched new timing denominators. Other arithmetic matrices are not rerun or ranked by this diagnostic.

Primary observation: unioned observed closed/different reached-argument threadCPU divided by same-observer outer defeq threadCPU, with absolute costs and all counters. Also report argument-call count/classes, censoring and timer errors, total capture elapsed and complete source outcomes. Do not multiply this fraction by the separate 35% sample into a claimed measured end-to-end bound. No count/flag fraction, theoretical erasure or diagnostic elapsed establishes GPU gain.

Use standard CLOCK_THREAD_CPUTIME_ID semantics, native compiler ABI, complete cohort accounting and the existing official-service whole boundary. A source reference to the clock API and an explicit statement of timing perturbation accompany the result. Structural-difference classification must not silently add expensive traversals to every timed call; either use the same native quick equality policy with charged cost or restrict its claim to pointer inequality and disclose the mismatch.

No performance effect is estimated from one instrumented run. This measurement characterizes one concrete diagnostic condition; it does not provide a confidence interval, stronger CPU ranking or final RQ4 result. Additional repeats are not predeclared because they would not cure a missing algorithm/readiness argument or instrumentation bias.

## Interpretation and scope

Positive: substantial observed paid child work survives the native shortcuts, meriting a concrete cost/readiness/algorithm proposal. Still no backend admission, system novelty or E2E gain.

Negative: the measured surviving closed child cost is too small to support a useful complete-cost implementation; close the closed-argument target without microkernel tuning and return effort to a higher-value mechanism.

Mixed/inconclusive: coverage, perturbation, incomplete work or context/phase association prevent the intended inference; keep the limitation and do not repeatedly repair/reprofile an unchanged weak target.

The evidence bounds one constructor/workload/route. It does not refute heterogeneous checking, the prepared-state thesis or the original four RQs. It can appear only as an opportunity/negative-operation-selection row inside the existing RQ4 evaluation, never as an independent systems contribution.
