\begin{abstract}
Formal verification services check related program and proof candidates that share libraries, declarations and accepted context.
Serving independent attempts requires balancing preparation reuse with candidate isolation because shared execution couples resource growth, contention and cancellation to worker isolation.
Native execution history extends beyond logical context to scope, heuristics, runtime objects and resource counters, so reconstructed context needs a separate argument about observable behavior.
Established caches, persistent environments, proof-state snapshots and bounded warm services recover preparation reuse, leaving unresolved the value of independent native execution at matched resources.
We argue that reusable state should retain preparation while separating each candidate's execution history and lifetime from preceding alternatives.
This separation requires supported quiescent boundaries, faithful native configuration and resource handling, and bounded memory as candidates modify branch-local state.
We study a proposed verification-service design that retains immutable prepared states in a parent, runs disposable independent branches with inherited native resource state and separate service accounting, and uses native execution for unsupported boundaries.
Using public Lean and satisfiability modulo theories (SMT)-backed candidate streams, we compare complete verification against competent bounded warm services and native logical or serialized prepared-state reuse, then assess remaining heterogeneous checking after preparation reuse on an RTX 5090 with setup, transfer and CPU fallback charged.

\section{Introduction}\label{sec:intro}
Formal verification services check streams of program and proof candidates against formal specifications. Related attempts from proof-generation systems share libraries, declarations and accepted context. Proof assistants construct and check proof terms, while program verifiers translate obligations into requests to satisfiability modulo theories (SMT) solvers. Community tools for Lean~\cite{lean4} serve these workloads through persistent environments~\cite{repl}.

Independent attempts require a service to balance preparation reuse with candidate isolation. Starting a verifier for each candidate repeats imports and parsing and replicates resident objects. Retained workers and shared logical environments avoid that repetition, but worker isolation determines their resource growth, contention and cancellation behavior. Concurrent attempts against one imported Lean context need the same context while retaining independent lifetimes. Cancelling one attempt must release its speculative work without ending the others.

Native execution history makes this balance depend on more than the visible formulas or declarations. In Z3's combined solver, an additional scope can change the selected solving path~\cite{z3api}, while earlier requests can alter heuristics and resource counters. Proof assistants also retain elaborator state and mutable runtime extensions beyond the immutable declaration environment~\cite{lean4,repl}. Reconstructing a logically equivalent context therefore requires a separate argument about observable verification behavior.

Established reuse recovers preparation, but its value relative to independent native execution at matched resources remains unresolved. Result caches avoid repeating completed work~\cite{boogieCache}, and the community read--eval--print loop (REPL) provides persistent environments, backtracking and pickling~\cite{repl}. Lean snapshotting retains elaborated proof state across parallel tactic branches~\cite{leanSnapshot}, and stock Lean saves incremental elaboration snapshots between invocations~\cite{leanIncremental}. Bounded warm services reuse environment roots and retire workers~\cite{kimina,kiminaPaper}, while Axle serves preloaded Lean contexts in separate request processes~\cite{axle}. Comparing against these native-reuse baselines must establish whether separating preparation from candidate execution history improves complete verification, cancellation and total memory across service processes.

We argue that reusable verification state should retain preparation while separating each candidate's execution history and lifetime. Preparing context before candidate evaluation makes that native state available to independent attempts. Each candidate inherits the prepared state, so preceding alternatives neither supply its solver history nor extend its lifetime. The benefit depends on the costs of preparation and branch creation and on the pages each candidate modifies.

Realizing this separation requires runtime safety, faithful resource handling and bounded memory. A branch must begin at a quiescent boundary that is safe for the verifier runtime. When process creation changes timers or descriptors, native configuration and resource accounting must remain faithful~\cite{fork}. Sharing must also improve capacity within a memory budget that bounds retained states. These requirements connect compatibility to the service's resource frontier, the achievable combinations of latency, throughput and memory use at matched CPU capacity and memory limits.

We study a verification-service design that retains immutable prepared states in a parent and executes candidates in disposable independent branches. Each branch owns its responses, mutable state, communication and cancellation, inherits native resource state, and receives separate service accounting. Supported quiescent boundaries, untouched candidate operations after preparation and bounded prepared-state lifetimes address runtime compatibility and memory use, with native execution for unsupported boundaries. We compare complete verification on public Lean and SMT-backed candidate streams against competent bounded warm services and native logical or serialized prepared-state reuse. After preparation reuse, we assess remaining heterogeneous checking on an RTX 5090, charging setup, transfer and CPU fallback to complete verification. \missing{Matched behavior results and end-to-end latency/throughput/memory findings, including the measured scope of device benefit.}

The evaluation tests four intended contributions. Section~\ref{sec:evaluation} distinguishes completed evidence from missing results.
\begin{itemize}
\item A characterization of sharing expensive preparation in actual ordered verification attempts (Section~\ref{sec:opportunity}).
\item A native branching design and an argument about observable behavior separating preparation from candidate interference (Section~\ref{sec:design}).
\item A bounded implementation integrating independent branches with native verification and cancellation (Section~\ref{sec:implementation}).
\item An equal-resource evaluation against established reuse, with a causal assessment of heterogeneous checking after preparation reuse (Section~\ref{sec:evaluation}).
\end{itemize}

\section{Background}\label{sec:background}
\subsection{Verification stages and outcomes}
Lean source verification includes parsing, elaboration, proof construction and kernel checking~\cite{lean4}. Imports prepare declaration environments before a candidate is elaborated, while kernel checking validates proof terms against the dependent type theory~\cite{lean4}. By contrast, post-export checker replay begins after the source frontend has already run. These boundaries distinguish savings in candidate construction, library setup and proof checking~\cite{leanArena,repl}.

SMT-backed verification includes frontend translation, solver setup, parsing, preprocessing and solving~\cite{verus,z3api}. A native SMT session can contain multiple queries and output requests. Solver responses include SAT for satisfiable queries, UNSAT for unsatisfiable queries, and UNKNOWN when the solver does not decide the query. Clients can also request models, proofs or unsatisfiable cores when the configured backend supports them~\cite{z3api}. These outcomes and artifacts define the comparison in Section~\ref{sec:behavior}.

An accepted Lean command may admit an unproved obligation using \texttt{sorry}~\cite{repl}. Complete proof verification distinguishes unfinished proof obligations and admissions from frontend diagnostics.

Closing a tactic's goals is also distinct from checking the enclosing modified declaration. LeanPolish tests tactic proposals against saved proof states before re-elaborating selected source edits~\cite{leanpolishPaper}. Its native menu screen restores state without separately finalizing each alternative as the original declaration~\cite{leanpolishSource}. A successful tactic screen therefore establishes a different outcome from acceptance of the enclosing declaration or source.

\subsection{Prepared native state}
A native execution prefix is an ordered sequence of verifier operations together with its configuration and runtime state. For SMT, this includes options, declarations, assertions and scopes in their observed order~\cite{z3api}. For Lean, it includes imports and accepted commands that establish the environment or proof state before the next attempt. Persistent tools provide ways to retain some of this state~\cite{repl,leanSnapshot}.

Native interfaces retain verification state, while runtime and resource properties determine how that state can be reused. The solver's own command interface saves state across evaluations~\cite{z3api}, and a resource limit can bound internal work independently of elapsed time~\cite{z3params}. Process branching shares existing memory through copy-on-write, but child timers, descriptors and runtime threads need separate handling~\cite{fork}. Section~\ref{sec:design} uses these native-state and process properties to define preparation boundaries.

\section{Motivation}\label{sec:motivation}
\subsection{Preparation and candidate lifetime}
A service must account for preparation reuse and candidate lifetimes. Preparation has value when attempts reuse expensive state, rather than merely share similar text. \missing{Final characterization of preparation CPU cost, memory and candidate fan-out from real Lean and SMT-backed streams.} A service must also account for attempts that are rejected, remain incomplete or exhaust their resources. Their lifetimes consume capacity even when the client seeks only one accepted candidate.

Established persistent sessions make cold process execution an insufficient performance baseline. The community REPL already allows multiple commands to refer to an earlier environment~\cite{repl}, and native proof-state snapshots support parallel tactic exploration~\cite{leanSnapshot}. We ask whether sharing native preparation changes concurrency, cancellation and aggregate memory relative to bounded versions of these services.

\subsection{Scope and history effects}
Logical equality of visible assertions does not establish equality of the native state. The distinction between logical context and execution history is observable in resource-bounded verification. \missing{Final native-session and prepared-branch comparisons, including scope-only and prior-history controls for status differences.} Scope effects can select a different solver path even in a fresh process~\cite{z3api}, while history effects can arise without a change to the candidate's explicit assertions. A compatibility argument must distinguish both causes from timing variability and account for native resource and runtime properties when establishing a faithful branch boundary.

The preparation/isolation tradeoff and scope/history distinction motivate the design in Section~\ref{sec:design}. Preparation sharing, candidate isolation and bounded resource use are evaluated together. A speedup from a path that changes the verifier responses or requested artifacts is excluded from the service comparison, even when that path remains logically sound on some inputs.

\section{Design}\label{sec:design}
The design has three goals derived from Section~\ref{sec:motivation}: (1) preserve the native verifier's observable behavior, (2) share expensive preparation while isolating candidate lifetimes, and (3) improve latency and throughput within matched CPU and memory resources. The service treats a prepared state as an immutable branching point. Candidate evaluation occurs only in an independent branch, and unsupported boundaries use native execution.

\subsection{Preparation boundaries}\label{sec:preparation}
A shared parent must represent state that every assigned candidate has available. The service therefore matches the original ordered preparation and configuration, without replacing them with a set of assertions. A candidate suffix begins after this preparation and includes its original scopes and output requests. The parent retains accepted context in the original preparation, but contains no learned or elaborated state produced by candidate suffixes after the selected boundary.

The boundary must also be safe for the runtime. Each adapter exposes a supported quiescent point with no pending candidate work or unresolved external effects. The service retains the prepared objects and initializes branch-owned communication and resource controls before evaluation. A runtime without such a point follows the native path. This restriction is a deployment boundary, not evidence that arbitrary native processes can be cloned safely.

\subsection{Observable behavior}\label{sec:behavior}
Native behavior is defined at the verifier interface, independently of the branch implementation. The reference is original native execution of the same ordered preparation and candidate suffix. This preparation retains the candidate's accepted context without inserting suffixes from preceding alternative candidates. History within the candidate's own native session remains part of its suffix.

Behavior comparisons cover verifier outcomes and requested artifacts. For Lean, the comparison includes diagnostics, completed proof obligations and admissions in each attempt. For SMT, it includes each SAT, UNSAT or UNKNOWN response and each requested artifact. Native proof or model validation checks artifact meaning where alternative valid artifacts can differ in representation. Counting accepted commands alone does not determine fidelity between verification paths.

The candidate executes its original suffix once in a branch. The service inserts no additional logical scope and performs no preparatory solver check to warm heuristics. Native solver resource state is inherited from preparation, while service CPU and elapsed costs are charged separately. These rules remove cross-candidate history as a source of difference, but wall-time limits and changed runtime conditions still require measurement rather than a universal assertion that responses remain equal.

The service chooses fallback according to interface compatibility, rather than treating every UNKNOWN response as a detector of divergence. Returning UNSAT when the native resource-bounded path returns UNKNOWN can also change client behavior. The service selects native execution when the adapter cannot support the boundary or requested artifact. Any residual mismatch in a supported comparison invalidates that path's fidelity claim. The service retains the mismatching case with its complete input and output.

\subsection{Branch lifetime and cancellation}
Candidate mutation should not force the service to retain the shared parent beyond its configured policy or affect another candidate. Each branch owns mutable candidate state and terminates after producing its response, while cancellation stops that branch and releases its private memory. Device work and buffers remain attributable to their candidate until completion or cancellation cleanup, which is included in branch lifetime and service accounting. The prepared parent remains available only while it satisfies the configured retention policy.

The lifecycle separates retained preparation from speculative work. A cancelled or incomplete attempt cannot become a new prepared parent. Branch failure returns an explicit native or service failure and leaves other branches independent. The evaluation includes failed attempts and cancellation recovery rather than reporting only successful candidate throughput.

\subsection{Bounded placement and execution}\label{sec:placement}
The benefit of preparation sharing must offset the costs of retained memory and branch mutation. The service admits prepared states within a memory budget and accounts for proportional shared memory and private dirty pages. Proportional set size (PSS) attributes each shared page across the processes sharing it~\cite{procMemory}, and fleet memory sums these attributed amounts across service processes. Placement favors states whose observed preparation work is reused often enough to offset the costs of creating and retaining those states. Branch concurrency is limited by CPU capacity and memory pressure, so copy-on-write sharing does not justify unlimited fan-out.

If candidates modify most retained pages, copy-on-write sharing can approach full replication. If preparation is cheap or locality is low, native execution avoids retention overhead. These cases test the same service tradeoff as workloads with substantial preparation sharing and define its measured operating range.

\subsection{Heterogeneous checking}\label{sec:device}
When preparation reuse removes repeated work, it leaves a smaller verification path for an accelerator to improve. The service selects expensive supported operations from profiles of that path and compares them with the strongest CPU implementation. For these checking operations, the input expression graph alone does not define dependencies, because reduction depends on binder environments and instantiated constants~\cite{lean4,nanoclo}. A GPU operation therefore includes its actual dynamic work, required representations and synchronization.

Supported device work preserves verifier semantics. Before a device operation is admitted, device qualification compares its outputs with matched CPU references. During execution, enclosing native verification checks the resulting proof or requested artifact where one is produced, and required online checks are charged to complete verification. Qualification does not imply a second full CPU replay on every request. Response and artifact fidelity follow Section~\ref{sec:behavior}, including UNKNOWN and responses without artifacts.

Unsupported work returns to CPU execution, whose cost remains in the complete verification measurement. Complete verification includes device initialization, representation construction, upload, download and queueing. We report operation speedups measured with data already on the device separately from complete checking.

\section{Implementation}\label{sec:implementation}
The artifact implements the native adapters and branch constructors used to test the design. It contains separate experimental
process-branch and shared-runtime state-branch constructors. These components
do not yet establish the complete bounded service proposed in
Section~\ref{sec:design}. Completed branch constructors have not demonstrated
an improved equal-resource service frontier. Their behavior and performance
results apply to the boundary and runtime version measured. The SMT adapter retains Z3's native command context across native parser invocations to evaluate ordered session state~\cite{z3api}. The Lean adapter uses the runtime boundary that prepares imports and accepted proof context before a candidate. For each verifier, qualification first compares fresh adapter execution with the original interface and then compares prepared branches with that reference. We measure reuse after these comparisons.

\subsection{Native adapters}
The native SMT command adapter is implemented in C++. It retains the command-line interface's command context and preserves the native order of configuration, manager creation and solver creation while evaluating original command sequences. It preserves options, scopes, checks and requested artifacts rather than reconstructing assertions through a different solver API.

Qualification compares fresh adapter execution with the matched standalone executable, using an unmodified executable built from the same source to distinguish build metadata from other response differences. This comparison separates interface incompatibility from differences caused by branching. Every observed response difference remains visible. Diagnostic branching tests can investigate a rejected adapter, but the service executes prepared-state branches only with an adapter that passes interface qualification.

A preparation boundary can separate parser invocations while retaining the native command context. Qualification therefore compares complete input, split native parsing and branch evaluation to distinguish parser end-of-input effects from branch effects.

For source verification backed by this SMT adapter, the measured interval also includes the native frontend's translation and its original solver interaction. Solver-session replay alone is reported at its narrower boundary.

For Lean, the adapter retains accepted context and keeps branch-local proof construction independent. It waits for source snapshots and the checked declaration environment before qualifying runtime quiescence, thread ownership and mutable extensions. Frontend completion alone does not establish that runtime workers, their finalizers and event loops have stopped. The adapter enables native process branching only after that separate runtime qualification.

\subsection{Arithmetic certificate reuse}\label{sec:arithmetic-oracle}
The arithmetic experiment tests whether reusing an external coefficient
certificate removes work that remains after native compilation and warm
environment reuse. FarkasFast selects hypotheses numerically and then invokes
stock arithmetic on the selected subset~\cite{farkasSource}.
That restricted invocation performs proof-producing normalization and another
certificate search. Our experimental path instead returns the numerical
certificate and constructs only the facts that it cites.

For each contradiction branch, the Lean frontend collects the applicable
assumptions and exports an arithmetic expression tree with stable identifiers
for opaque atoms. A native untrusted process expands rational polynomials,
generates nonlinear products and square facts, and performs support search
with exact certificate repair. It returns nonnegative coefficients, equality
orientations and the provenance of any selected product or square.
Lean constructs those selected facts, forms their weighted sum and uses its
native arithmetic discharger to check the resulting contradiction.
The enclosing declaration still undergoes ordinary native checking.

One certificate check here means one weighted contradiction per solved branch,
not one check for an entire tactic or source. For example, an equality goal
can require two contradiction branches. The external search does not return
trusted Lean expressions or replace the kernel. Unsupported syntax, a missed
certificate or failed reconstruction restores the saved tactic state and
selects the same Fast/hybrid and product-reuse path as the comparator.
All failed attempts and fallback work remain in whole-source timing.

The current exporter directly handles real and rational arithmetic.
Natural and integer arithmetic and unsupported normalization remain on the
fallback path, so supported invocation counts alone cannot establish useful
cost coverage. This prototype uses CPU native code. Batching products on
an RTX 5090 remains conditional on measured eligible work and complete
preparation, transfer and fallback costs. External arithmetic search and
native certificate checking are established techniques~\cite{farkasSource,mathlib},
so their presence alone does not establish systems novelty.

\subsection{Shared-runtime native state}
The shared-runtime Lean constructor retains the prepared native command state
while assigning each candidate a separate mutable-reference context. Reads of
prepared reference cells use the retained base until a destructive operation
creates a private cell. Unresolved prepared thunks are evaluated privately.
Branch identity follows admitted native tasks, and branch release waits for
those tasks and their execution scopes before releasing retained identities and
private versions.

This reference overlay does not make arbitrary native globals, extensions,
external effects or foreign-function interfaces (FFI) private. Listed guarded
effects select native replay. When unsupported effects terminate a worker, the operational outcomes remain
recorded. These mechanisms establish neither general process
equivalence nor completed cancellation qualification. The process constructor
in Figure~\ref{fig:architecture} and this runtime constructor have different
supported boundaries and isolation properties.

\subsection{Process and resource handling}
Linux copy-on-write branches retain the parent address space, with candidate writes creating private pages~\cite{fork}. The parent stays quiescent and never executes candidate suffixes, while branch communication uses separate descriptors. The service reaps children after response, cancellation or failure and distinguishes native solver resource counters from service elapsed and CPU accounting.

Cancellation instrumentation records the native progress reached before termination and whether the child was reaped before later work. The records show reaping after native progress. Establishing interruption inside a check requires separate execution-phase records.

Qualification of supported boundaries covers native resource controls affected by process creation. Claims about wall-time outcomes are limited to the measured operational scope described in Section~\ref{sec:behavior} and the evaluation limitations, rather than following from inherited counters alone.

The design requires bounded prepared-state retention and branch concurrency using the preparation-reuse criterion in Section~\ref{sec:placement}. Prototype instrumentation records parent and child proportional memory, private dirty memory and process lifetimes. These counters alone do not establish the proposed placement policy or a complete service frontier. This accounting distinguishes shared preparation from full worker replication and includes replacement costs.

\subsection{Device path}
The device path uses an allocated RTX 5090 through NVIDIA's container runtime~\cite{nvidiaContainerToolkit}. During device qualification, a CPU reference and GPU implementation consume the same identified input and preserve output identity for each supported checking operation. Required online checks follow Section~\ref{sec:device}. Native artifact fidelity follows Section~\ref{sec:behavior}, and complete verification includes CPU fallback and device/runtime costs. For checker representation, existing techniques include expression layouts with integer identifiers and delayed substitution~\cite{nanoclo,nanocloFortran}, so their use does not establish a new checking algorithm.

The Linux implementation integrates native SMT session evaluation in C++, Lean context reuse and matched CPU/device execution through these adapters.

\section{Evaluation}\label{sec:evaluation}
The evaluation examines four research questions, each mapped to the design goals and contribution it tests. RQ1 tests the sharing opportunity characterized by the first contribution. RQ2 tests behavior preservation and isolation, the first two design goals, while RQ3 tests the third goal, the equal-resource service frontier. RQ4 tests whether heterogeneous execution improves that frontier for complete verification after reuse.
\begin{description}
\item[RQ1] How much expensive native preparation can real verification candidate streams share across independent jobs?
\item[RQ2] Does branching from prepared native state preserve verifier responses and requested artifacts while isolating candidates and cancellation?
\item[RQ3] How does prepared-state branching change end-to-end latency, throughput and memory at equal resources compared with established warm-session reuse?
\item[RQ4] After preparation reuse, when does heterogeneous execution improve complete verification over the strongest measured CPU path?
\end{description}

\subsection{Preparation sharing}\label{sec:opportunity}
RQ1 asks how much expensive native preparation real verification candidate streams share across independent jobs. \subsection{Limitations}
The service applies at supported native boundaries and retains the verifier as the authority. Supported backend versions and mutable runtime extensions constrain deployment. Logical equivalence alone does not promise equal resource-bounded responses. Wall-time limits depend on machine load and execution speed, so the evaluation states their operational scope separately from deterministic work limits. Valid negative and mixed results bound the claimed operating range.

Public generated attempts are replay workloads, whose arrivals can differ from a deployed multi-user service. Fixed published proof corpora remain useful controls but do not establish real candidate fan-out. Full GPU Lean checking is a distinct result from acceleration of a metadata primitive, and GPU certificate proving is a distinct workload from ordinary proof checking.

\section{Discussion}
Separating preparation from candidate execution connects native behavior to service resource use. Sharing preparation can reduce replication, while each candidate's mutation and lifetime determine how much of that sharing survives. The matched comparison therefore accounts for behavior, cancellation and fleet memory together, rather than treating retained context alone as the service benefit. Extending the service to another verifier requires a supported runtime boundary and qualification against its original interface.

\section{Related work}
\paragraph{Persistent verification state.}
Persistent Lean environments and native proof-state snapshotting retain elaborated context across attempts~\cite{repl,leanSnapshot}. Stock Lean also saves full elaboration or post-import snapshots~\cite{leanIncremental}, while Kimina provides bounded warm verification with environment reuse~\cite{kimina,kiminaPaper}. These mechanisms provide the direct comparison for preparation reuse. The service evaluates independent native execution, cancellation and bounded fleet resources in addition to logical environment branching. This distinction requires matched evidence, rather than a novelty claim for snapshots themselves.

LeanPolish already restores native tactic state, resumes unchanged commands from saved checkpoints and supports persistent import workers~\cite{leanpolishSource}. Its released proof-improvement attempts include failed alternatives, while menu screening and later source verification have different boundaries~\cite{leanpolishPaper}. These existing mechanisms strengthen the native-reuse comparison. Failure collection and saved-state execution are established baseline capabilities.
LeanTree factorizes proof states according to metavariable dependencies,
supporting state reuse and parallel proof search~\cite{leantree}.
Independent proof goals and reusable intermediate states are therefore
established mechanisms. A new service must demonstrate its additional
behavior and resource benefit.

Axle combines preloaded Mathlib with per-request processes~\cite{axle}.
Its published normalized-sample comparison measures computation rather than
the complete public service path. Isolated preloaded serving is therefore
existing work, and our complete behavior and resource comparison with unchanged sources
must establish any additional benefit.

\paragraph{Verification caching.}
Fine-grained verification caching avoids rechecking unchanged program regions~\cite{boogieCache}. The service comparison combines competent caching with warm execution, so cold startup cannot account for the entire claimed advantage. Caching and session reuse retain different parts of verification work. Native session reuse retains incremental command history and requested-artifact state~\cite{z3api}. Reconstruction with equivalent assertions remains a different execution history from the original native stream.

SHRED supplies exact rooted-prefix profiling and a closing-proof reuse prototype
keyed by elaborated context and target, with native proof checking and fallback~\cite{shred}.
Reusing expensive proof construction is therefore also established work.
A distinct mechanism needs evidence beyond the presence of repeated tactics
or a large acceleration for a selected cache hit.

\paragraph{Prepared execution.}
Prepared execution and copy-on-write sharing are established systems mechanisms. SOCK and SEUSS share prepared state to reduce startup and increase parallel service density~\cite{sock,seuss}. Spice reduces disk snapshot restoration costs by co-designing the storage layout and kernel restore mechanisms~\cite{spice}. A contribution beyond these prepared-execution systems requires more than specialization to verification. Our comparison tests whether native behavior and bounded shared preparation together require and benefit from a verification-specific execution mechanism.

\paragraph{Heterogeneous checking.}
GPU and CPU checker representations address different parts of verification. Nanoclo uses delayed substitutions, and nanoclo-fortran stores kernel objects in parallel arrays with integer identifiers~\cite{nanoclo,nanocloFortran}. These checkers are direct competitors to representation-only acceleration. Our heterogeneous evaluation asks about the expensive dynamic checking that remains and complete verification costs, rather than extrapolating from input graph width.


Learned Lean feedback instead predicts verdicts and compiler messages on
GPUs~\cite{learnedLeanFeedback}. Its throughput comparison has different output
semantics from native verification, and its hybrid training rewards can use
predictions for unfinished checks. This is complementary evidence about an
accuracy--cost tradeoff, rather than exact native checking acceleration.


\paragraph{Certified arithmetic and batched linear programs.}
Mathlib and Farkas already separate arithmetic certificate search from native
proof construction~\cite{farkasSource}. Exact certification of external linear
programming results, including infeasibility and unboundedness, is also
established~\cite{verifiedLP2025}. Gurung and Ray assign a CUDA block to each
linear program and evaluate both batch supply and complete application
performance~\cite{batchedLPGPU2019}. These precedents cover the numerical
primitives used in our heterogeneous prototypes. Their presence alone cannot
establish a new verification service or predict a gain under limited
concurrent request supply. Our comparison charges proof construction, exact
repair, failed searches and independent cancellation at matched resources.

\section{Conclusion}
Native preparation and candidate execution history are separate resources in verification serving. Independent branches retain preparation while isolating candidate lifetimes, and their value depends on behavior fidelity and the equal-resource service frontier. \missing{Final findings answering all four RQs, including the measured heterogeneous scope.} The matched comparison determines whether branching supplies a systems benefit beyond existing warm reuse.
